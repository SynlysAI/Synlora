# SynlysAgent 后续演进路线（v2）

> 基线：2026-09-16，`0.10.0-beta.1`（内测版）。
> 关系：本文接续 `2026-09-12-synlysagent-06-backlog-roadmap.md`。06 的阶段一（沙箱升级 / 能力市场 / 内置内容统一）已全部完成；阶段二的未完成项在本文**重新排序**，并补入 06 未识别的缺口。06 保留为历史记录，进度以本文为准。
> 用法：checkbox 跟踪；每项含目标、做法、验收标准与成本估计；动手前可展开为独立实施计划（走 superpowers 计划流程）。

---

## 0. 两个已确认的前提

**前提 1 — 近期要推 Spec_Agent 异步任务。**
因此**统一 Job 注册表（C1）是全局最高优先级**：它是异步任务的唯一地基，其余能力（5 种谱图任务、SpecLabOS 设备工作流）都建在它上面。阶段 A / B 与 C1 并行推进，不阻塞 C1 开工。

**前提 2 — 接受 `workers=1` 单实例约束。**
运行时（`ActiveRun` / SSE 队列 / ask future）是单进程内存态，多副本会破坏 steer / answer / cancel。结论：**不做 run 状态外置与水平扩展**，改为在部署与运维层面明确单实例、补保活与崩溃恢复（B3）。因此**原 06 阶段二·8 的「双进程 RPC → headless 运行时」保持暂缓**，无外部触发不做。

---

## 1. 判断依据：当前框架的强弱面

**强的（不必再投入）**：Agent 能力面已经相当完整——事件会话内核、四段工具管线、turn/step 双层循环、steering 插话、`Permission.ASK_USER` 强制审批、上下文自动压缩、LLM 退避重试、docker 沙箱强隔离、插件机制（一切皆插件）、三层能力可见性模型、用户自建技能与专家。这些构成了"能跑起来"的完整闭环。

**弱的（本文重点）**：**产品化运维面几乎是空白**——用量看不清、成本无闸门、用户管不了、数据没备份、部署迁移脆弱、没有 CI。这部分在单机内测阶段无感，一旦多人使用就会立刻暴露，且**无法靠加 Agent 能力弥补**。

据此，本文的排序原则是：**先把"多人用不出事"补齐（A/B），再纵深化能力（C）**；其中 C1 因前提 1 单独提前。

## 2. 阶段总览

路线分**两条轨道**，不是串行：**C 轨是主线**（由外部依赖驱动、有时间压力），**A/B 轨是运维面**（迟早要做、不阻塞主线）。下文 A/B/C 的编号是分类，不表示执行顺序。

| 轨道 | 内容 | 预估 |
|---|---|---|
| **主线（先做）** | 统一 Job 注册表 → Spec_Agent 异步任务 → SpecLabOS 设备工作流 | 3 + 3 + 2 天 |
| **运维面（并行插空）** | A 内测期打磨 → B 多人用之前必须 | A 4~5 天 · B 9~10 天 |
| **纵深（触发式）** | 长期记忆 · MCP adapter · 多 Agent | 按触发条件表启动 |

### 建议的开工顺序（单人视角）

| # | 项 | 预估 | 为什么排在这个位置 |
|---|---|---|---|
| 1 | **C1 统一 Job 注册表** | 3 天 | 主线地基，下游 C2 / C3 都等它 |
| 2 | **A3 可观测性** | 2 天 | **必须赶在 C2 之前**：异步任务上线即需要回答"任务跑到哪了、谁提交的、失败在哪步、烧了多少 token"，没有审计与用量聚合就是瞎的 |
| 3 | A1 工具 spill · A2 CI 流水线 | 0.5 + 0.5 天 | 零依赖、顺手清掉 |
| 4 | **C2 Spec_Agent 异步任务** | 3 天 | 此时地基与可见性均已就位 |
| 5 | A4 会话导出 | 1 天 | 由内测反馈驱动 |
| 6 | B 轨各项 | 9~10 天 | 出现第二个使用者即启动，见第 3 节触发点表 |

## 阶段 A：内测期打磨

### A1. 工具结果 spill

- [ ] **目标**：`post-execute` 不再对超限结果纯截断，改为"有界预览 + 可寻回定位符"
- [ ] **做法**：超限结果落工作区 `tmp/spill-{call_id}.txt`，落事件的 content 换成前约 2KB 预览 + locator（完整结果路径），模型可经 `file.read` 分段读回；参考 DSH `packages/spill/`
- [ ] **验收**：`python.run` 打印超大 DataFrame → 上下文只占预览大小 → 模型能按 locator 读回任意段落；断连重放后 locator 仍有效
- [ ] **成本**：0.5 天 · **依赖**：无

### A2. CI 流水线

- [ ] **目标**：push / PR 自动跑全量校验，取代本地手跑
- [ ] **做法**：`.github/workflows/ci.yml`，两个 job——Python（`pip install -e packages/synlys-harness` + `-e apps/web/backend[dev]` → 两个 pytest）+ 前端（`npm ci` → `npm run build` + `npm run lint`）；docker 沙箱用例无 daemon 自动 skip，不阻塞
- [ ] **验收**：push 触发、全绿；任一失败阻断合并；build 时间可接受（< 10 分钟）
- [ ] **成本**：0.5 天 · **依赖**：无

### A3. 可观测性基础

拆三个可独立验收的子项，建议按序做（3.3 依赖 3.2 的落表）。

- [ ] **A3.1 结构化日志**：请求级中间件输出 JSON 行日志（request_id / user_id / session_id / method / path / 状态 / 耗时）；应用日志统一走同一 logger，PM2 日志可直接检索
- [ ] **A3.2 工具调用审计**：每次工具执行落一条审计记录（user_id / session_id / tool / 参数摘要 / 耗时 / 结果状态 / `sandbox` 标记 / 错误摘要），管理后台可查；**参数摘要需截断且敏感字段脱敏**（插件配置类参数不入审计）
- [ ] **A3.3 用量聚合**：按 用户 / 模型 / 日期 聚合 token 用量（in / out / 合计），提供 `GET /api/v1/admin/usage`，管理后台出看板
- [ ] **验收**：管理员能回答「上周谁用了多少 token」「哪个模型最贵」「哪些工具最常失败」「某次报错的具体请求」；三步都不需要翻 PM2 原始日志
- [ ] **成本**：2 天 · **依赖**：无

### A4. 会话导出

- [ ] **目标**：把一次会话导出为可分享的 Markdown
- [ ] **做法**：后端 `GET /api/v1/sessions/{id}/export?format=md`，**从事件流投影**（不读 DB 副本，保证与回放一致）；内容含用户消息、助手回答、思考折叠摘要（可选开关）、工具调用摘要、产物清单与路径；前端会话菜单加「导出」
- [ ] **验收**：导出文件结构完整、中文不乱码、工具调用有摘要而非噪声；导出结果可直接发给同事看懂
- [ ] **成本**：1 天 · **依赖**：无

## 阶段 B：多人用之前必须

### B1. 管理员用户管理页

- [ ] **目标**：管理后台补「用户」页，管理员能看人、管人
- [ ] **做法**：用户来源按后端分支——mongodb 模式读 `ai4ms.users`，sqlite 模式读 `local_users`；列表含 用户名 / 角色 / 状态 / 创建时间 / 磁盘用量 / token 用量（接 A3.3）；支持启用 / 禁用、改角色
- [ ] **验收**：管理员能看到全部用户；**禁用后该用户已有 token 立即失效**（校验链路上生效，而非仅前端拦截）；单用户用量与配额可见
- [ ] **成本**：2 天 · **依赖**：A3.3（用量列）

### B2. LLM 用量配额

- [ ] **目标**：给 LLM 花费装上闸门（当前只有磁盘配额，token 无上限）
- [ ] **做法**：按用户配置 日/月 token 预算（缺省取全局默认），落库；`agent_service` 装配 run 前检查余额，超限直接拒绝并给出明确错误码与提示文案；额度按自然日/月自动重置；管理员可对单用户豁免或临时提额
- [ ] **验收**：设置预算后，用户超额被拒且前端提示清晰（不是笼统报错）；次日自动恢复；管理员提额后立即生效；**拒绝发生在调用 LLM 之前**（不产生已扣费的空跑）
- [ ] **成本**：1.5 天 · **依赖**：A3.3

### B3. run 崩溃恢复

- [ ] **目标**：进程重启后会话不卡死、插话不静默丢失
- [ ] **做法**：① steering 队列持久化（进 session 事件或独立 inbox，重启可读回）；② 启动时 **session repair**——把 DB 中处于 RUNNING 的 run 标记为 `interrupted`，事件流补一条终止事件；③ 前端对 `interrupted` 会话显示明确状态与「继续」入口。参考 DSH `inbox` / `repair`
- [ ] **验收**：run 进行中 `kill` 进程 → 重启后会话**不显示"运行中"**、用户可继续发言、历史完整可回放；未消费的插话要么按策略重放、要么在界面上明确标记丢弃（不静默消失）
- [ ] **成本**：2 天 · **依赖**：无（与前提 2 兼容，正是单实例下的兜底手段）

### B4. 应用容器化

- [ ] **目标**：一条命令起全栈，摆脱"conda 路径写死 + 源码部署"
- [ ] **做法**：多阶段 Dockerfile（前端 build 产物 → 后端运行时镜像，注意 `catalog/` 必须与 `app/` 同级同放）+ `docker compose`（app + mongodb + 数据卷）；`ecosystem.config.cjs` 的 PM2 路径保留为备选部署方式
- [ ] **待决问题**：容器内如何使用 docker 沙箱——挂载 `docker.sock`（简便但容器逃逸面变大）vs 沙箱服务独立部署（干净但多一跳）vs 容器内保持 `SANDBOX_MODE=local`（最差）。**动手前需先定这个决策**
- [ ] **验收**：`docker compose up` 起全栈；数据卷持久化、重启数据不丢；健康检查通过；前端页面与 API 同端口可达
- [ ] **成本**：2 天 · **依赖**：B4 决策项先定

### B5. 备份与数据迁移

- [ ] **目标**：数据能恢复，字段能演进
- [ ] **做法**：① **备份**——`data/` 目录（sqlite + workspaces + sessions）与 mongodb 的定时快照脚本 + 保留策略，写进运维文档；② **迁移**——引入 schema 版本文档（如 `schema_meta` 集合），启动时按版本顺序执行迁移函数，替代当前"靠代码兼容"的隐式做法
- [ ] **已知缺口（2026-09-16 实测）**：`SqliteStore.init()` 用 `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`，对**已存在**的表是 no-op——给老集合新增索引列时新列不会被加上，紧随其后的 `CREATE INDEX` 会抛 `no such column`，**直接崩在启动**。当前 `jobs` 是全新建表故未踩到；任何"给既有集合加索引列"的改动都必须先落迁移方案
- [ ] **验收**：能从备份完整恢复到一个可用实例；加一个字段后启动自动迁移，老数据可正常读写；迁移幂等（重复执行不产生副作用）
- [ ] **成本**：2 天 · **依赖**：无

## 阶段 C：能力纵深（AI⁴MS 接入主线）

### C1. 统一 Job 注册表 ★ 最高优先级

> 实施计划：[2026-09-16-synlysagent-14-job-registry.md](2026-09-16-synlysagent-14-job-registry.md)（14 个任务，可独立端到端验收）

- [ ] **目标**：异步任务的地基，让"提交即返回、完成自动唤醒"成为通用能力
- [ ] **做法**：
  - `jobs` 存储：稳定 job_id + 所属 会话/用户 + 外部系统 id
  - 统一状态机 `PENDING / RUNNING / COMPLETED / FAILED / CANCELLED`；各子平台的内部状态由 **Connector 映射**到该状态机（见集成设计稿 §12/13）
  - **完成通知唤醒 agent**（免轮询）：任务完成事件投回会话，触发一次续跑，把结果整合进对话
  - 工具面：`job.submit` / `job.status` / `job.list` / `job.cancel`
- [ ] **验收**：提交一个长任务 → **提交立即返回 job_id（不阻塞当前 step）** → 完成后 agent 自动唤醒并整合结果 → 用户可查进度、可取消；进程重启后未完成 job 状态可恢复（配合 B3）
- [ ] **成本**：3 天 · **依赖**：无（但 B3 会显著提升其可靠性）

### C2. Spec_Agent 异步任务工具化

- [ ] **目标**：5 种谱图解析任务接入，替代当前同步三件套的长阻塞形态
- [ ] **做法**：`/api/v1/tasks/{nmr,gpc,...}` 提交建在 C1 上；**按用户身份调用**（服务端代签短效 token，机制已就绪，见后端 README「按用户身份调用」）；任务归属按用户隔离，避免多用户串号
- [ ] **验收**：对话提交一个 NMR 任务 → agent 自行跟踪 → 完成后自动整合结果；两个用户同时提交互不串号、互不可见
- [ ] **成本**：3 天 · **依赖**：C1

### C3. SpecLabOS 设备 / 工作流接入

- [ ] **目标**：接入实验管理平台，危险操作人工确认
- [ ] **做法**：工具声明 `Permission.ASK_USER`（管线已支持强制审批，声明即生效）；设备与工作流操作走审批卡
- [ ] **验收**：调用触发审批卡 → 允许才执行 → 拒绝则工具返回拒绝结果且 agent 能继续对话；fail-closed（审批通道异常时拒绝执行）
- [ ] **成本**：2 天 · **依赖**：C1（若涉及长任务）

### C4. 跨会话长期记忆（工作区级）

- [ ] **目标**：同一工作区内跨会话记住偏好与结论
- [ ] **做法**：`memories` 存储（维度 `user_id + project_id`，含来源会话 id）；`on_session_end` 钩子 LLM 抽取候选 → 去重合并入库；会话装配时检索 top-N 注入 system prompt（带"参考记忆"标注）
- [ ] **开关**：`memory_enabled` **默认关**（照 jiuwen 惯例），管理页可切
- [ ] **遗忘**：会话删除**不**级联删记忆（记忆独立于会话）；管理页提供查看 / 删除入口
- [ ] **验收**：工作区 A 的会话里告知的偏好，同工作区新会话能遵守；开关关闭时零记忆注入
- [ ] **成本**：2 天 · **依赖**：无

### C5. MCP adapter

- [ ] **目标**：一次投入换第三方工具生态
- [ ] **做法**：Tool Registry 加 MCP 来源（stdio / HTTP transport），启动时拉取工具 schema 并注册；工具命名空间 `mcp.<server>.<tool>`，与助手工具白名单兼容；凭证与启停管理进管理后台
- [ ] **验收**：接入任一现成 MCP server（如 filesystem），工具卡片正常展示与执行；启停与凭证在管理页可配
- [ ] **成本**：3 天 · **依赖**：无

### C6. 多 Agent / SwarmFlow

- [ ] **触发条件**：出现"多专家并行协作"的真实需求（**未出现不做**）
- [ ] **前置**：assistants 已具备 teammate 定义原料（persona / 工具白名单 / 模型 / 知识库绑定）
- [ ] **做法**：harness 加 subagent provider（fork 事件会话 + 工具面收窄）；声明式 team 装配（借鉴 jiuwenswarm `agents/swarm/`）；前端团队消息展示 + 轨迹面板
- [ ] **验收**：一个 leader + 2 专家（文献综述 / 实验设计）协作完成综合报告
- [ ] **成本**：5 天+ · **依赖**：C1（长任务编排）

## 3. 决策触发点（什么时候启动什么）

| 信号 | 启动项 |
|---|---|

## 4. 本文明确不做（保持与 06 一致）

- 按角色 / 按用户白名单的细粒度可见性
- 插件市场远程下载、用户自建 / 导入**插件**
- 双进程 RPC / headless 运行时（前提 2）
- 移动端适配
- 图表交互渲染（保持图片展示）
